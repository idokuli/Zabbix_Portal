1 What Is Overwatch?

Overwatch is the internal monitoring control plane for your infrastructure. It sits in front of a Zabbix monitoring server and adds:

  • Role-based access control — operators, team leads, admins, and auditors each see different things
  • Team management — group users into teams with assigned hosts
  • Portal LDAP authentication — sign in with your Active Directory credentials; your portal account is created automatically on first login
  • Simplified workflows — add monitoring to a host, define custom alert rules, bulk-import hosts from CSV/Excel, and export inventory
  • Live problem feed — real-time alerts with sound, desktop notifications, and acknowledgement
  • Custom dashboards — build your own widget layouts from Zabbix graphs and metrics, saved per-user or per-team
Overwatch does not store your metrics All monitoring data comes from Zabbix in real time. Overwatch is a control and visibility layer on top of Zabbix — it keeps its own database only for portal users, teams, dashboards, alert rules, acknowledgements, and notes.

2 Logging In

Local login

  1. Open the Overwatch URL in your browser.
  2. Enter your username and password.
  3. Click Sign In.
Forgotten password? Passwords can only be reset by an administrator. Contact your team lead or an admin — they can set a new password from the Users page.

Portal LDAP login

If your organisation uses Active Directory or another LDAP directory, Overwatch can authenticate you with your network credentials. This is separate from Zabbix's own LDAP settings — it is configured inside Overwatch and only applies to portal logins.

  1. On the login page, click Sign in with LDAP (appears below the standard Sign In button when Portal LDAP is enabled).
  2. Enter your LDAP username (usually your Windows login, not the full email address).
  3. Enter your LDAP password.
  4. Click Sign In.
Username capitalisation does not matter Portal usernames are case-insensitive. Signing in as idokuli, IdOkUlI, or IDOKULI all resolve to the same account — matching how LDAP/AD itself treats usernames. You will never get a second, duplicate account for typing your name with different capitalisation.
First login The first time you sign in via LDAP, Overwatch creates your portal account automatically with the Operator role. Your team lead can adjust your role and assign you to a team afterwards.
Administrators: enabling Portal LDAP Portal LDAP is configured in Users Management → Authentication → Portal Login. See the Portal LDAP setup guide in the Users section below.

3 The Interface

Top bar

A single row across the top of every page: the Overwatch logo, a search field (also opens the ⌘K command palette), the active-problems count, the Backend API / Zabbix status dots, the notification bell, the alert settings menu, the dark/light mode toggle, and your user menu (name, role, logout).

Activity rail & section panel

Navigation is two columns on desktop, VS Code-style:

ElementDescription
Activity railThe narrow icon-only column on the far left. Each icon is one top-level section (Overview, Hosts, Dashboard, Monitoring, Services, Reports, Data Collection, Alerts, Users, Administration). Click an icon to switch sections.
Section panelThe wider column next to the rail, showing the current section's sub-pages as a list. Sections with no sub-pages (Overview, Hosts) don't get one — the rail alone is enough.
Collapsing the panelClick the already-active rail icon again, or use the < chevron in the panel's own header, to hide it and give the page more width. A thin handle stays in its place — click it (or the rail icon again) to bring the panel back.

On a phone or narrow window, the rail and panel are replaced by a hamburger menu (top-left) that opens the full navigation as a drawer.

Status dots

The two coloured dots in the top bar update every 15 seconds:

  • Backend API — green means the Overwatch backend is running and reachable
  • Zabbix — green means the backend can reach your Zabbix server
Red status dot? If either dot is red, data across the portal will be stale or unavailable. See Troubleshooting.

Data refresh

Most pages refresh automatically on a configurable interval (10 seconds by default). You do not need to manually refresh your browser. The interval can be adjusted by an administrator via the REFRESH_INTERVAL environment variable — no image rebuild required.

Your personal settings

A number of preferences are remembered per browser, in local storage — not on your account. They do not follow you to another machine or another browser, and they are never shared with other users:

  • Dark / light theme
  • Alert sound on/off and the chosen sound preset
  • Desktop notifications on/off, and whether they stay on screen
  • The Problems tab's sort order and "hide acknowledged after" delay

4 Roles and Permissions

RoleWhat they can do
RootFull access to everything. Can manage all users, teams, and system settings. Can grant any role.
Team LeadCan manage users within their team, assign hosts, see all admin sections, and unacknowledge problems (reopening them). Cannot manage other team leads or root users.
OperatorCan create, edit, and delete hosts and monitoring configuration (items, triggers, host groups) within their team, view metrics and problems, and acknowledge alerts. Cannot create or delete users or change system settings. The default role assigned to LDAP users on first login.
MemberRead-only access to the team's hosts and monitoring data. Cannot make changes or acknowledge problems.
AuditorRead-only access across all teams. Can view everything but cannot make changes. Only Root can grant this role.

A user can hold multiple roles simultaneously. When a higher role is selected, all lower roles in the hierarchy are automatically selected too (Windows-style cascade). You cannot assign a role higher than your own.

The admin sections (Data Collection, Alerts, Users, Administration) are only visible in the activity rail for Root and Team Lead roles. The underlying API endpoints are independently gated — a missing nav icon is not the only access control.

Restrictions

Independent of roles, a user can also have one or more restrictions, set in the same form used to assign their role (see Users). A restriction removes write access to one specific area even though the user's role would otherwise allow it — read access is never affected.

RestrictionSectionRemoves
Host GroupsData CollectionCreating, renaming, deleting host groups, or changing their membership
ItemsMonitoringCreating, editing, or deleting items on any host
TriggersMonitoringCreating, editing, or deleting triggers on any host

For example, an Operator with the Items and Triggers restrictions can still add hosts and manage host groups, but every "Add Item" / "Add Trigger" action is blocked. Root always bypasses restrictions.

5 Section Guide

Overview

The overview page is your main health dashboard. It shows:

  • Total hosts and how many are currently available vs. unreachable
  • Active problems count broken down by severity
  • Recent problems — a live list of the most recent Zabbix trigger events
  • Per-team summary — how many hosts and active problems each team owns

Hosts

Hosts are shown in a sortable table — click any column header to sort ascending, click again for descending, and a third time to clear the sort. Use the search field to filter by name or IP.

Adding a host

  1. Click Add Host.
  2. Fill in: Hostname, IP address, Host group (required), and Templates (optional).
  3. Click Save.

Importing hosts from CSV or Excel

  1. Click Import.
  2. Download the template first to see the required column format.
  3. Required columns: host (or hostname) and ip. Optional: template.
  4. Upload your file and confirm.

Exporting hosts

Click Export to download the full host inventory as an Excel file (.xlsx). The export includes: Hostname, IP, DNS, Status, Availability, Proxy, Host Groups, Templates, and Description.

Deleting a host

Open the actions menu on the host row and choose delete. A confirmation dialog will appear.

Deletion is permanent Deleting a host removes it from Zabbix. All associated items, triggers, and history are deleted and cannot be recovered.

Dashboard

The Dashboard lets you build custom widget layouts from your Zabbix graphs and last-metric values. Layouts are saved automatically and can be scoped to you personally or to your whole team.

Adding widgets

  1. Click Add Widget.
  2. Choose a widget type:
    • Graph — a Zabbix native graph for a selected host
    • Last Value — the current reading of a single metric
    • Recent Items — a table of the most recently added monitoring items
  3. Configure the widget and click Save.

Pages

Dashboards support multiple named pages. Use Add Page to create tabs within your dashboard, and drag widgets between them.

Saving and sharing

  • Save as mine — only you see this layout
  • Save for team — all team members see the same layout
If no graphs appear on a graph widget, the host either has no graph definitions configured in Zabbix or is currently unreachable.

Each graph widget's time-range dropdown ranges from 1 minute up to 6 months (1M / 3M / 6M presets after 7d). How far back data actually appears depends on your Zabbix server's own trend retention — see Troubleshooting if an older range comes back empty.

Monitoring

The Monitoring section has six tabs (Latest Data through Alert History below), plus two standalone pages reached from the same rail group: Items and Triggers.

Latest Data

Shows the last collected value for every monitored item on a selected host. Use the search box to filter by item name or key, the Host dropdown to pick a specific host, and the Status dropdown to show only enabled or disabled items.

Status chipMeaning
EnabledItem is active and collecting
DisabledItem exists but is paused
No dataItem has not reported within its expected interval — usually means the host agent is unreachable
A yellow banner appears at the top of the table when the host agent is unreachable. All items will show No data until the agent comes back online.

Item Graphs

Time-series charts for item values. Select a host and an item, then choose a time range to view historical data — from 1 minute up to 6 months (1M / 3M / 6M presets after 7d). You can zoom in by dragging on the chart.

Problems

Shows all currently active Zabbix trigger problems, using Zabbix's own six-level severity scale and colours:

SeverityZabbix valueNotes
Disaster5Highest severity
High4
Average3
Warning2

Not classified0Lowest severity

Filtering, searching, and sorting

  • Search — filter by problem name or hostname.
  • Filter by group / Filter by host — narrow to a host group or a specific host.
  • Severity chips — click the chips above the list to show only certain severities.
  • Sort by — Severity (default) keeps the highest severity first and the most recent first within each severity; Newest first and Oldest first sort purely by when the problem started.
  • Clear filters — resets search, host, group, and severity filters in one click.

Click any row to expand it and see full host detail, duration, notes, and — if acknowledged — who acknowledged it, when, and their note.

Acknowledging a problem

  1. Find the problem in the Problems tab.
  2. Click Ack on the right side of the row.
  3. Enter an optional note.
  4. Click Acknowledge.
Acknowledging marks the problem in Zabbix and records who did it in Overwatch's audit log. The problem itself stays open until its trigger condition clears in Zabbix — acknowledging is a statement that a human is on it, not a fix. It also stops the repeat-ring for that problem.

Unacknowledging a problem (Team Lead+)

If a problem was acknowledged too early — the fix didn't hold, or it needs a second look — a Root or Team Lead can reopen it:

  1. Find the acknowledged problem in the Problems tab.
  2. Click Unack next to the green Ack'd chip.
  3. Enter an optional reason.
  4. Click Unacknowledge.
Unacknowledging clears the acknowledgement in Zabbix and Overwatch, so the problem re-enters the alert workflow — including the repeat-ring, if it's still unacknowledged 5 minutes later. The reason (if any) is recorded as a note on the problem, alongside who unacknowledged it and when. Unack only appears for Root and Team Lead accounts — Operator and Member cannot unacknowledge.

Auto-hiding acknowledged problems

If your list fills up with problems that are already being handled, use the Hide acked after dropdown to make acknowledged problems disappear from your view after a delay: Never (the default), 1 minute, 5, 15, 30 minutes, 1 hour, or 4 hours.

Once a problem is acknowledged, its row shows a live "hides in …" countdown next to the green Ack'd chip, so nothing vanishes without warning. When the countdown reaches zero the row drops out of the list on its own.

This only changes your view — nothing is closed in Zabbix Hiding is a display filter in your browser. The problem remains open and active in Zabbix, and it is still visible to colleagues who have not set a hide delay. If the same trigger clears and then fires again later, Zabbix issues a brand-new event, so it will reappear in your list as a fresh, unacknowledged problem.

Adding a note

The note icon next to Ack lets you leave a note on a problem without acknowledging it — useful for logging what you've tried so far, or leaving a note on a problem someone else already acknowledged. Notes are independent of acknowledgement: you can add any number of them, on acknowledged or unacknowledged problems alike.

  1. Click the note icon on the problem row.
  2. Type your note.
  3. Click Add note.

A count badge appears next to Ack once a problem has one or more notes. Expand the row to read the full thread — each note shows who wrote it and when.

Problem History

Shows resolved (past) problems within a selected time window. Pick a time range (1h / 6h / 24h / 7d / 30d) and optionally a minimum severity to search historical events. Unlike the Problems tab, this includes problems that have already been resolved.

Alert Rules

Custom threshold-based alerts defined in Overwatch (separate from Zabbix triggers). These run on a 15-second check loop by default.

  1. Click Add Rule.
  2. Select the host and item to watch.
  3. Choose the operator (>, <, =, etc.) and threshold value.
  4. Set the severity.
  5. Optionally assign a custom alert sound for this rule.
  6. Click Save.
When a rule fires, a notification card appears in the bottom-right corner and is logged in the Notification Center. The rule stays active until the value drops back past the threshold.

Alert History

A log of all alert-rule events — when each rule fired and when it resolved.

Items

Add a monitoring item to a host by picking an item type (Agent, HTTP, SNMP, Database, Script, and around a dozen others) and filling in its form — each type asks for what it needs (a URL for HTTP checks, an OID for SNMP, a script for Script items, and so on).

Auto-create trigger Every item type's form has an Auto-create trigger toggle. Turn it on and the portal creates a matching trigger the moment the item is saved, instead of you having to switch to the Triggers page afterward:
  • For numeric items (Float, Integer), set an operator and threshold (e.g. > 90) and the trigger fires when the value crosses it.
  • For string, log, or text items, set a match type (contains / does not contain / matches regex / does not match regex) and a pattern, and the trigger fires when the item's value matches it.
  • Leave the threshold or pattern blank on either side and the portal creates a "no data" trigger instead — useful for items where there's nothing sensible to compare against (an HTTP check or process-up item that just returns 0 or 1) but you still want to know if it stops reporting.
You also pick a severity for the trigger, same as creating one manually.

Triggers

Lists all triggers across your hosts, with severity and current state. Use Add Trigger to create one manually against an existing item, with the same numeric-threshold or string-pattern choice described above.

Services & SLA

Services

Lists all Zabbix services (logical business nodes such as "Payment API" or "Database Cluster"). You can create, edit, and delete services here. Services can be nested — a parent service aggregates the status of its child services.

SLA

Lists SLA definitions. Each SLA has a target uptime percentage, a measurement period (weekly, monthly, quarterly, or annually), and service tags that define which services it applies to. Click the SLA row to view a detailed report broken down by period.

SLA is a Zabbix 6.0+ feature. If your Zabbix version is older, the SLA tab will always be empty.

Health Monitors

Simple URL or host reachability checks (HTTP GET / ICMP) that are surfaced as service items. Use this tab to add lightweight uptime monitoring without writing full item definitions.

Users (Admin only)

Users page

Lists all portal users. Root sees all users platform-wide; Team Leads see only their own team. You can create, edit role assignments, change passwords, and delete users here.

Role assignment rules You cannot assign a role higher than your own. Only Root can assign the Auditor role. When selecting a higher role, lower roles are automatically selected too.

Teams

Teams group users with a shared set of assigned hosts. A user can belong to multiple teams simultaneously — they will see the union of all their teams' hosts.

Creating a team

  3. Use Assign Server to assign hosts to the team.

User rows

Each member row is expandable — click it to reveal:

  • Display name — full name from LDAP/AD (shown only when it differs from the login)
  • Email — if set

The collapsed row shows the display name as the primary label (falls back to the login name for local accounts).

Removing a user from a team

Click the trash icon on a member row to remove that user from this team only. Their portal account is not deleted and they can be re-added at any time. To delete a user account entirely, use the Users page.

User Groups

Zabbix-side permission groups (separate from portal teams). Manage which Zabbix user groups exist and add/remove members.

User Roles

Zabbix permission profiles — control which Zabbix UI sections and API calls each role can access.

API Tokens

Zabbix API tokens for external integrations. Only Root can create and delete tokens.

Authentication

The Authentication tab has two sections: Zabbix Settings (the Zabbix server's own authentication config — LDAP, SAML, HTTP auth) and Portal Login (Overwatch's built-in LDAP connector for portal users).

Portal Login — enabling LDAP authentication

This allows users to sign into Overwatch with their Active Directory / LDAP credentials. Accounts are created automatically on first login with the Operator role.

  1. Go to Users Management → Authentication → Portal Login.
  2. Toggle Enable LDAP Authentication on.
  3. Fill in the connection details:
    • LDAP Host — the address of your LDAP/AD server (e.g. ldap.company.com or an IP address)
    • Port — 389 for plain LDAP; 636 for LDAPS
    • Use SSL — enable for LDAPS (port 636)
    • Base DN — where to search for users, e.g. DC=company,DC=com
    • Bind DN — a service account Overwatch uses to search the directory, e.g. CN=overwatch-svc,OU=Service Accounts,DC=company,DC=com
    • Bind Password — the service account password
    • User Search Filter — how to find a user by their login name, e.g. (sAMAccountName={username}) for Active Directory
  4. Click Test Connection to verify the settings before saving.
  5. Click Save.
Active Directory user search filter For most AD environments: (sAMAccountName={username})
For OpenLDAP: (uid={username})
The {username} placeholder is replaced with whatever the user types in the login box.
Bind DN credentials The Bind DN account needs read access to the directory — no write permissions required. Store its password securely. Rotating the service account password requires updating the Portal LDAP config and saving again.
What happens when an LDAP user logs in On first login, Overwatch creates a portal account tagged source=ldap with the Operator role, and stores their username in lowercase so capitalisation never produces a duplicate account. The Team Lead or Root can then change the role and assign the user to a team. If the LDAP server is unreachable, LDAP login fails gracefully — local accounts, including root, are never affected.

6 Notification System

In-app popup cards

When a new problem fires, a notification card appears in the bottom-right corner. Each card shows: severity, how long ago it fired, host name, problem description, and — for real Zabbix problems — a snooze icon.

  • Not classified, Information, and Warning cards auto-dismiss after 8 seconds
  • Average, High, and Disaster cards stay until you dismiss them
  • If more than 3 stack up, a Dismiss all link appears

Repeat-ring for unacknowledged problems

An alert that nobody acted on is easy to miss with a single beep. Overwatch keeps ringing:

Every 5 minutes, until acknowledged or snoozed As long as a real Zabbix problem stays unacknowledged, its alert sound repeats every 5 minutes — not just once when it first fires. This stops as soon as the problem is acknowledged, or the resolved trigger clears in Zabbix.

To silence the repeat-ring for one problem without acknowledging it, click the snooze icon on its popup card and pick a duration: 5, 15, or 30 minutes, or 1 hour. The problem stops repeat-ringing until the snooze expires, then resumes if it's still unacknowledged. Snoozing is per-browser and does not acknowledge the problem — it stays visible and open to everyone else.

Alert-rule events (the custom threshold alerts under Monitoring → Alert Rules) don't have a Zabbix acknowledgement state, so they don't repeat-ring or offer a snooze — only real Zabbix problems do.

Notification Center

Click the bell / inbox icon in the top bar to open the Notification Center. It has two tabs:

TabWhat it shows
Alert HistoryEvery notification received, persisted to your account. You can acknowledge directly from here.
Active ProblemsAll currently open Zabbix problems. You can acknowledge from here too.

Mark all as read clears the unread badge without deleting history. Clear history hides current entries — new notifications will still appear.

Alert settings menu

Everything below lives in one place: the tune / slider icon in the top bar, tooltipped Alert settings.

SettingWhat it does
Alert sound Master on/off for audible alerts. Higher severity plays more beeps at a higher frequency.
Desktop notifications Turns operating-system notifications on or off. These appear over other applications (Windows Action Center / macOS Notification Center), so you see them even when the portal is behind another window.
Keep notifications on screen On by default. Pins each desktop notification until someone dismisses it, instead of letting it fade after a few seconds. Turn this off if you prefer notifications that disappear on their own.
Sound preset Choose Beep, Chime, Ping, or Alarm — or upload your own audio file. Presets are synthesised in the browser, so they work fully offline.

Turning on desktop notifications

  1. Open the Alert settings menu in the top bar.
  2. Switch Desktop notifications on.
  3. Your browser will ask for permission the first time — click Allow.
  4. Leave Keep notifications on screen on if you want alerts to wait for you.
Notifications not disappearing fast enough to read? That is what Keep notifications on screen is for — with it on, the popup waits in your notification centre until you click or dismiss it, so a busy operator can never miss an alert that fired while they were looking elsewhere.
What desktop notifications need in order to work
  • The portal must be open in a browser tab. The tab can be minimised or in the background, but if the browser is fully closed, no notifications are sent.
  • The site must be served over HTTPS (or localhost). Browsers disable the notification API entirely on plain http://.
  • Browser and operating-system notification permissions must both be granted.
  • Keep notifications on screen relies on a Chromium/Windows behaviour. Chrome and Edge honour it; Safari ignores it and will still auto-dismiss.
If the toggle is greyed out, the browser permission was previously blocked — see Troubleshooting.

7 Releases and CI/CD Pipeline

This section explains how Overwatch is built, tested, and deployed. It is relevant to team leads and operators who want to understand what version is currently running, how updates get promoted to production, and how to tell if an environment is out of date.

How releases work

Overwatch is deployed from a GitLab CI/CD pipeline. The pipeline runs only when a version tag is pushed (e.g. v1.4.0). Branch pushes and merge requests do nothing in CI — they are code review steps only.

This means:

  • Every deployment is traceable to an exact tag with a release note.
  • No code reaches staging or production without an intentional tag.
  • Rolling back is always possible — every deployed version is a known image tag.
Two repositories The application repo holds the code and builds the container images. A separate GitOps repo holds the Helm charts, the per-environment values.yaml files, and the ArgoCD Application manifests. The application pipeline never deploys to a cluster directly — it writes new image tags into the GitOps repo, and ArgoCD applies them.

Pipeline stages

When a tag is pushed, the pipeline runs through these stages in order:

StageWhat happensAutomatic or manual?
Detect Compares the new tag against the previous tag to determine which apps actually changed (backend and/or frontend). If nothing in an app changed, its build and promote work is skipped. Also validates that all required CI variables are set — fails immediately if any are missing. Automatic
Lint Static checks: YAML lint (yamllint) on all pipeline files; Python lint (ruff), Python type-check (mypy), JavaScript lint (Biome), and TypeScript type-check (tsc) for changed apps only; plus a SonarQube scan. Automatic
Build Docker images are built using Kaniko (rootless, daemonless) and pushed to the private container registry tagged with the release version (e.g. :v1.4.0). Only changed apps are built — an unchanged backend is never rebuilt. Automatic
Promote The push-image-tags job clones the GitOps repo, updates the image tag in environments/{staging,production,dr}/values.yaml for each changed app, then commits and pushes. This is the only job that writes to the GitOps repo. Automatic
Bootstrap: staging Idempotently creates or updates the staging ArgoCD Application via the ArgoCD API, so the app is registered without anyone clicking through the ArgoCD UI. Automatic
Bootstrap: production / DR Same for production and DR — but each is a manual gate in the pipeline. Someone has to press play. Manual (GitLab)

Who actually rolls out the new version

ArgoCD does, not the pipeline. Once the new image tag is committed to the GitOps repo:

EnvironmentPurposeRollout
Staging Test every tag before it reaches users. Fully functional; data is isolated from production. Automatic — ArgoCD auto-syncs when the GitOps repo changes
Production The live environment users access. Manual — ArgoCD shows OutOfSync; an operator clicks Sync after validating staging
DR (Disaster Recovery) A standby deployment on a separate cluster, used to fail over if the production cluster is unavailable. Manual — click Sync in ArgoCD after production is confirmed healthy

What "changed" means

The detect stage compares which files changed between the previous release tag and the current tag:

  • Only apps/frontend/ changed → only the frontend image is built and re-tagged. The backend keeps its current tag.
  • Only apps/backend/ changed → only the backend is rebuilt. The frontend is untouched.
  • Both changed → both are rebuilt.
  • Nothing changed → the promote job exits as a no-op.

This means a frontend change never forces an unnecessary backend restart, and vice versa.

How to know what version is running

In the ArgoCD UI, open the Application for the environment you care about (one per environment — staging, production, DR). The Summary tab shows the current Git revision synced and the image tags in use. The Git tag name is the image version — the v1.4.0 tag built images tagged :v1.4.0.

From the cluster directly:

kubectl get deployment -n <namespace> \
  -o jsonpath='{.items[*].spec.template.spec.containers[*].image}'

Rollback

If a deployment causes a problem, administrators can roll back to the previous version without touching the code. In the ArgoCD UI: open the Application → History and Rollback → select the last known-good revision → click Rollback. ArgoCD re-applies the chart and image tags from that Git revision immediately.

Alternatively, edit the image tag directly in the GitOps repo's environments/<env>/values.yaml and push — ArgoCD picks up the change (staging auto-syncs; production and DR require a manual Sync click).

How to check what was previously deployed In the ArgoCD UI, the History and Rollback tab for each Application lists every sync with its Git revision, timestamp, and status. Pick the last Succeeded entry before the problem started.

8 Troubleshooting

SymptomWhy it happensHow to fix it
"Backend API" dot is red The frontend cannot reach the Overwatch backend service. Check the backend pod is running: kubectl get pods -n <namespace>. Read its logs if crashing: kubectl logs <pod-name>. Locally: make sure the backend server is started.
"Zabbix" dot is red The backend is running but cannot connect to Zabbix. Verify ZABBIX_URL, ZABBIX_USER, and ZABBIX_PASS are correct. Try logging in to the Zabbix web UI directly with those credentials. Check backend logs for ZabbixAPI errors.
"Invalid credentials" on login Wrong username or password. Check caps lock on the password — usernames are case-insensitive, passwords are not. Ask an admin to reset your password. Default first-time credentials: Admin / admin.
LDAP login fails — "Authentication failed" Wrong LDAP credentials, or Portal LDAP is misconfigured. Confirm you are using your network/AD username (not your email address). Ask an admin to check the Portal LDAP config in Users Management → Authentication → Portal Login, and use Test Connection to verify the settings.
"Sign in with LDAP" button is not visible Portal LDAP is not enabled. A Root user must enable it in Users Management → Authentication → Portal Login.
Audit Log always shows the same user (e.g. "Admin"), regardless of who actually made the change This is expected — Overwatch talks to Zabbix through one shared service account for every write, so Zabbix's own Audit Log can only ever show that account, never the real portal user. Check the Portal Actions report tab instead (Reports → Portal Actions) — it records the real logged-in user for every change made through Overwatch.
Desktop notifications toggle is greyed out The browser notification permission for this site was previously set to Block. Sites cannot re-prompt after an explicit block. In Chrome, click the icon left of the address bar → Notifications → Allow. Or open chrome://settings/content/notifications, remove the site from Not allowed to send notifications, then reload the page and toggle it on again.
Desktop notifications are on, but nothing appears Blocked at the browser or OS level, or the site is not on HTTPS. Check the address bar shows https:// (the notification API is disabled on plain http://). Confirm Chrome's global setting is "Sites can ask to send notifications". In Windows, check Settings → System → Notifications allows Chrome, and that Focus Assist is not suppressing toasts.
Notifications disappear before I can read them Keep notifications on screen is switched off, so the OS auto-dismisses them. Turn it on in the Alert settings menu. Note that Safari ignores this setting — use Chrome or Edge if you need pinned notifications.
The alert sound keeps beeping every few minutes The problem is still unacknowledged. Overwatch repeats the alert sound every 5 minutes until it's acknowledged or snoozed — see Repeat-ring for unacknowledged problems. Acknowledge the problem, or click the snooze icon on its popup card to silence just that problem for a while. Turn off Alert sound in the Alert settings menu to stop all audible alerts.
"Unack" button is missing on an acknowledged problem Unacknowledging is limited to Root and Team Lead roles. Expected for Operator, Member, and Auditor accounts. Ask a Team Lead or Root user to reopen the problem, or acknowledge/resolve it in Zabbix directly.
An acknowledged problem vanished from the Problems tab Hide acked after is set to a delay, so acknowledged problems drop out of the list once the countdown expires. Expected behaviour — the problem is still open in Zabbix. Set Hide acked after to Never to keep acknowledged problems visible. See Auto-hiding acknowledged problems.
Page shows no data / tables are empty Backend or Zabbix is unreachable, or the host has no configured items. Check both status dots are green. Try a full page reload. Confirm the host has items configured in Zabbix.
Graph is empty (or only partly filled) when a 1M/3M/6M range is selected Overwatch will query Zabbix as far back as you ask, but Zabbix itself only keeps trend data for as long as its own Data storage period (trends) housekeeping setting allows — commonly shorter than 6 months. A Team Lead or Root user can check this under Administration → Housekeeping: look at Data storage period (trends) (in days) and make sure Enable internal housekeeping for trends is on. If it is shorter than the range you selected, older data was already purged by Zabbix and cannot be recovered by the portal.
"Host agent unreachable" banner Zabbix cannot collect data from the host's agent. Confirm the host is powered on. Check the agent service: systemctl status zabbix-agent. Check firewall rules — Zabbix needs port 10050 (passive) or 10051 (active).
Acknowledged problem — badge did not update The badge refreshes on the auto-refresh interval (10 seconds by default). Wait a few seconds. If it still does not update, refresh the page.
Export downloads empty or corrupted file Backend unreachable, or no hosts exist to export. Confirm both status dots are green. If the host list is empty, the export will only contain headers.
Custom alert rule is not firing The check runs every 15 seconds, or the item is not collecting data. Wait up to 15 seconds after the threshold is crossed. Check Latest Data for that item — it should not show a No data chip. Verify the operator and threshold are correct.
SLA tab is always empty No SLAs defined in Zabbix, or Zabbix version is older than 6.0. Confirm SLAs exist in Zabbix directly. Verify the Zabbix service account has read access to services.
Cannot assign a role / option is greyed out You are trying to assign a role higher than your own. Ask a Root user to make the change.
Dashboard widget shows "No graphs available" Host has no graph definitions, or the host is unreachable. Confirm graph definitions exist in Zabbix (Monitoring → Hosts → Graphs). Confirm the host has templates applied.
Staging was deployed but production still shows the old version Production requires a manual sync — it is never deployed automatically. Open the ArgoCD UI, find the production Application (it will show OutOfSync), and click Sync.
My theme / sound / filter settings reset These preferences are stored per browser, not on your account. Expected on a new machine, a different browser, or after clearing site data. Set them again from the top bar.

Still stuck?

Check these in order:

  1. Backend logs — kubectl logs <backend-pod> -n <namespace> (or docker logs backend locally).
  2. Browser console — open Developer Tools (F12) → Console tab. API errors appear there.
  3. Network tab — Developer Tools → Network. Look for red (failed) requests to /api/*. The response body usually contains the error message.
  4. Zabbix directly — log in to the Zabbix web UI to confirm whether the issue is in Zabbix or in Overwatch.
